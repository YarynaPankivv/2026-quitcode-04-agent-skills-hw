# Режими відповіді вебхука й тестовий / production URL

## Який режим обрати

Режим задає вузол Webhook в n8n (Respond). Від нього залежить, що отримує Next.js і чи можна
чекати відповідь.

| Режим n8n | Що отримує Next.js | Коли | Як поводиться наш код |
|---|---|---|---|
| **Immediately** | 200 одразу після прийому | Подія «до відома», результат не потрібен: `lead-created`, аналітика | `after(() => triggerN8n(…))`, без `callbackUrl` |
| **When Last Node Finishes** | Вихід останнього вузла після завершення | Швидка довідка (секунди), результат потрібен у відповіді | Лише якщо людина підтвердила, що воркфлоу гарантовано короткий; таймаут 10 с |
| **Using 'Respond to Webhook' Node** | Те, що задає Respond to Webhook | **Стандарт для довгих задач:** 202 `{"job_id": …}` одразу, результат — колбеком | Запис `queued` → `after(() => triggerN8n(…, { callbackUrl }))` → колбек переводить у `ready`/`failed` |
| Streaming | Потік | Не використовуємо | — |

**Правило 100 секунд.** Усе, що може наблизитися до 100 с, — лише асинхронно (202 + колбек). На
n8n Cloud запит, на який вебхук не відповів за 100 с, завершується **524**. Воркфлоу при цьому
працює далі, а Next.js про результат уже не дізнається. **Не певен, скільки триває воркфлоу, —
він асинхронний.** Синхронне очікування довгого воркфлоу — правило зупинки.

Навіть у синхронному режимі форма не тримає користувача на спінері: або коротка довідка з
таймаутом, або асинхронно.

**Respond to Webhook** спрацьовує один раз, наступні такі вузли ігноруються. Воркфлоу завершився,
не дійшовши до нього, — n8n відповідає 200 зі стандартним повідомленням; помилка до нього — 500
(ми повторюємо 5xx, тож ідемпотентність потрібна й тут).

## Тестовий і production URL

| | Тестовий | Production |
|---|---|---|
| Шлях | `/webhook-test/<event>` | `/webhook/<event>` |
| Працює | 120 с після «Listen for test event» (або ручного запуску) | Поки воркфлоу **опублікований** |
| Дані видно в редакторі | Так | Ні |

- У коді, `.env.example`, тестах, документації проєкту — **лише** `/webhook`. Тестовий URL людина
  може тимчасово поставити у свій `.env.local`, коли дивиться дані в редакторі; агент його нікуди
  не пише.
- Симптом тестового URL у проді: «заявки мовчки губляться» — n8n відповідає 404, а код, який
  не дивиться на статус, вважає, що все добре. Тому статус відповіді завжди перевіряємо.
- n8n 2.x: публікація фіксує версію воркфлоу; production-виклики йдуть у неї, а не в останні
  правки. Після змін — Publish знову.
- На self-hosted шляхи `webhook` / `webhook-test` можна перейменувати (`N8N_ENDPOINT_WEBHOOK`,
  `N8N_ENDPOINT_WEBHOOK_TEST`). Якщо клієнт це зробив — записати в `docs/n8n-integrations.md`
  проєкту й спитати людину, як назвати базу в `.env.example`.

## Мок: як відтворити кожен режим локально

Мок — `scripts/mock-n8n.mjs` цього скіла (у LeadDesk та сама копія — `tools/mock-n8n.mjs`).
Запускати з кореня проєкту; секрети — з `.env.local` через `--env-file`, ніколи прапорцями.

| Що перевіряємо | Команда |
|---|---|
| Immediately | `node --env-file=.env.local <skill>/scripts/mock-n8n.mjs` |
| Синхронний режим, 2 с | `… --mode last-node` |
| 524, як на Cloud | `… --mode slow --cloud-timeout 5000` |
| Асинхронний 202 + підписаний колбек через 5 с | `… --mode respond-202 --delay 5000` |
| Тестовий URL (лише 120 с) | `… --listen` |

Журнал мока показує метод, шлях, статус, тривалість, **імена** заголовків, розмір і sha256 тіла,
`auth=ok|missing|wrong|none`, `idempotency=new|repeat|absent` і рядки `callback POST … -> <код>`.
Значень і тіл він не друкує — тож його можна вставляти у звіти.
